# CLAVIS — расписание экосистемы

Цель — вся мультиплатформенная система: один протокол, держатели Android, iOS, Linux и Windows, верификатор, инструмент эмитента, издатель снимка реестра. Каналы расширения, старой формы, NFC, BLE и QR входят в расписание после того, как держатели и верификатор говорят одним протоколом.

## Что проверено на машинах

- NAS, этот компьютер: `192.168.1.114`, `aarch64`, hostname `NAS`, rustc 1.97.0. Проводник остаётся здесь.
- Телефон по ADB: `R5CT92MDXRH`, `SM_S908E`, `device`, `usb:3-1`. Очередь `android-device-queue` в момент проверки была свободна.
- Beast `192.168.1.112`: ping отвечает, SSH пользователем `beast` отвечает, hostname `beast`, `x86_64`. Android SDK на месте, clang NDK `27.2.12479018` есть, JDK 17 есть, symlink `/usr/lib/jvm/java-17-openjdk-arm64` есть. rustc 1.100.0 поставлен в домашний каталог пользователя `beast`. Чужие SDK не переносились.
- Mac mini в `/home/pi/Documents/shared/hosts` нет. Объявлены `beast`, `MyNUC`, `NAS`. Адрес Mac не назначен. Сборка iOS не запускалась.
- MyNUC `192.168.1.108`, пользователь `akona`, SSH ответил: компьютер `MYNUC`, Microsoft Windows 10.0.26300. Двоичный файл Windows там не собирался.

## Решения

- Ядро и программы Linux, Windows, верификатор, эмитент и реестр — один Cargo workspace на Rust. Крейты: `clavis-protocol`, `clavis-holder`, `clavis-holder-linux`, `clavis-holder-windows`, `clavis-ffi`, `clavis-verifier`, `clavis-issuer`, `clavis-registry`.
- Профиль реализации: Ed25519, дерево Меркла SHA-256, презентация шифруется X25519 и ChaCha20-Poly1305. Идентификаторы профиля — `did:key`. Метод DID продукта сменный и этим профилем не выбирается.
- Лист — SHA-256(`0x00 || путь || 0x00 || значение`). Узел — SHA-256(`0x01 || левый || правый`). Нечётный узел поднимается. Ключ AEAD — HKDF-SHA256 общего секрета X25519, info `clavis-presentation-v1`. Допуск часов в программах — 120 секунд. Тесты подставляют время.
- Канал держатель–верификатор — кадры с длиной по TCP в локальной сети. HTTP, расширение, NFC, BLE и QR несут те же объекты позже. ADB — установка и экран, не канал протокола.
- Держатель, который открывает владелец на подключённом телефоне, — приложение Android. Оно вызывает `clavis-ffi`. Имена Android API в протокол не входят. `minSdk` 26, `compileSdk` 35, ABI `arm64-v8a`, NDK `27.2.12479018`, JDK 17.
- iOS вызывает тот же символ `clavis_profile`. Сборка — на Mac mini, когда он объявлен. Пока его нет, проект лежит в репозитории, успех сборки не заявляется.
- Windows-держатель — крейт workspace. Сборка двоичного файла на MyNUC выполняется на своём срезе, после проверки SSH.
- Сборка Android и тяжёлый Rust идут на Beast, когда ping и SSH отвечают. Недостающее ставится рядом с чужими SDK. На NAS та же сборка запускается только если Beast не отвечает. Проводник на Beast не переносится.
- Установка и экран телефона — `android-device-queue` на NAS, проект очереди `CLAVIS`, серийный номер `R5CT92MDXRH`. Отдельный замок телефона не вводится.
- Ключ устройства живёт за чертой `Module` и верификаторам не показывается. Тестовый модуль создаёт неизвлекаемый ключ и отказывает в экспорте. Это не TPM. Единая функция `boot` не пускает сборку устройства, если платформенного модуля нет.
- Попарный ключ презентации — отдельный на верификатора и тоже не экспортируется.
- У индекса, журнала и каждого контейнера свой ключ. Одна выдача открывает один контейнер.
- Восстановление — парольная фраза оборачивает ключи данных и переоборучивает их на новый ключ устройства. Старый ключ устройства она не восстанавливает. Сервера проекта нет.
- Якорь эмитента отделён от реестра просящих. У верификатора якорь клиники в локальной конфигурации. Реестр этого контура — подписанный локальный снимок одного доверенного учреждения. Нет снимка, просрочка или чужая подпись дают «категория не проверена».
- Медицинская запись — W3C Verifiable Credential в JSON-LD, который читает FHIR-ориентированный верификатор, плюс одна самозаявленная запись. Портрет входит в презентацию только если он есть в запросе.
- Режим доверенного оператора — динамический запрос, одно подтверждение, свежесть возвращается, повтор отвергают держатель и верификатор.
- Удаление — подписанное заявление. Журнал не смотрит в базу верификатора.
- Вне расписания пусто.

## Срезы

Закрытый срез диспетчер заново не открывает: его приёмка уже проходит.

### S01 — Объекты презентации

- что: запрос, презентация, свежесть, одно запрошенное поле, удержанное второе поле, шифрование на ключ верификатора.
- зависит: нет.
- машина: NAS.
- приёмка: `cargo test -p clavis-protocol --test presentation_release -- --exact freshness_one_field_encrypted_to_verifier`
- состояние: закрыт.

## Два цикла

В `main` пишет только приёмка.
Диспетчер каждые 20 минут открывает ветку только для открытого среза, зависимости которого уже в `main` и у которого нет открытой ветки.
Приёмщик каждые 10 минут вливает ветку только когда приёмка этого среза прошла и diff совпадает с концепцией `docs/clavis-whitepaper.html`.
Проводник живёт на NAS: Android-сборка уходит на Beast, когда Beast отвечает, установка и экран идут через `android-device-queue`.
Оба цикла останавливаются, когда проходит приёмка S22.
