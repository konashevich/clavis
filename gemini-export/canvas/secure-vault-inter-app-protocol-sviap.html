Protocol Specification: Secure Vault Inter-App Protocol (SVIAP)

1. Introduction

The Secure Vault Inter-App Protocol (SVIAP) defines a platform-independent method for a Holder (the Vault application) to securely store, authorize, and transmit Verifiable Credentials (VCs) to Verifiers (external applications). The protocol mandates the use of a hardware-backed security module (HSM, TEE, SE, or TPM) for all cryptographic operations.

---

2. Protocol Entities (DID Roles)

  • Holder (H): The application managing the user's decentralized identity and hardware-protected keys.
  • Verifier (V): An external application or service requesting a Verifiable Presentation of specific data points.
  • Issuer (I): A trusted third party (e.g., a Doctor or Bank) that has cryptographically signed a credential.
  • Hardware Security Module (HSM): The platform's secure environment used for key generation and biometric-gated operations.
  • Subject (User): The individual to whom the credentials belong.

---

3. Cryptographic Prerequisites

  1. Decentralized Identifier (DID): Each entity is identified by a unique URI (e.g., did:sviap:user123).
  2. Holder Identity Keypair ($S_{H}, P_{H}$): Asymmetric keys stored in the HSM used to sign Verifiable Presentations.
  3. Verifier Encryption Key ($P_{V}$): An ephemeral public key provided by the Verifier to secure the data transfer.

---

4. Logical Dataflow (The VC Handshake)

Phase I: Credential Storage

  1. Hardware Attestation: $H$ verifies the device has a TEE/SE.
  2. Encryption: $I$ issues a signed VC. $H$ encrypts this VC using a hardware-protected master key ($K_{M}$) before saving to local storage.

Phase II: Presentation Request

  1. Discovery: $V$ sends a Presentation Request to $H$ containing:

* Input_Descriptors: Specific fields required (e.g., name, license_number).
* Verifier_DID: The identity of the requester.
* Public_Key_V: $P_{V}$ for the secure delivery channel.
* Nonce: A challenge to ensure freshness.

Phase III: Subject Authorization

  1. Consent UI: $H$ resolves the Verifier_DID against the Trust Registry (Entry #3 in Draft Notes) and prompts the user.
  2. Biometric Gate: The HSM releases the keys required to generate a Verifiable Presentation only upon successful biometric authentication.

Phase IV: Verifiable Presentation (VP) Delivery

  1. VP Generation: $H$ extracts the requested fields and signs them with $S_{H}$ to create a Verifiable Presentation.
  2. Peer-to-Peer Encryption: $H$ re-encrypts the VP using the Verifier's public key ($P_{V}$).

* $Ciphertext = Encrypt_{P_{V}}(VP + Nonce)$

  1. Transmission: $H$ returns the encrypted VP to $V$.

---

5. Security Principles

5.1 Hardware-Bound Presentation

Unlike software-only wallets, the private key $S_{H}$ never leaves the TEE. A "Presentation" cannot be spoofed or replayed because the hardware requires a fresh biometric trigger for every unique Nonce.

5.2 Purpose Binding & Non-Repudiation

Every VP includes a Purpose_Statement and an Expiry_Timestamp. Because the VP is signed by the Holder's hardware-backed key, it provides an immutable record of what was shared and why.

5.3 Verifier Accountability

The Verifier must provide a valid did:sviap that is cross-referenced with the Operator Trust Hierarchy. Unverified DIDs trigger "Non-Registered" warnings (Entry #3).

---

# Protocol Specification: Secure Vault Inter-App Protocol (SVIAP)

## 1. Introduction
The **Secure Vault Inter-App Protocol (SVIAP)** defines a platform-independent method for a **Holder** (the Vault application) to securely store, authorize, and transmit **Verifiable Credentials (VCs)** to **Verifiers** (external applications). The protocol mandates the use of a hardware-backed security module (HSM, TEE, SE, or TPM) for all cryptographic operations.

---

## 2. Protocol Entities (DID Roles)
* **Holder (H):** The application managing the user's decentralized identity and hardware-protected keys.
* **Verifier (V):** An external application or service requesting a **Verifiable Presentation** of specific data points.
* **Issuer (I):** A trusted third party (e.g., a Doctor or Bank) that has cryptographically signed a credential.
* **Hardware Security Module (HSM):** The platform's secure environment used for key generation and biometric-gated operations.
* **Subject (User):** The individual to whom the credentials belong.

---

## 3. Cryptographic Prerequisites
1.  **Decentralized Identifier (DID):** Each entity is identified by a unique URI (e.g., `did:sviap:user123`).
2.  **Holder Identity Keypair ($S_{H}, P_{H}$):** Asymmetric keys stored in the HSM used to sign Verifiable Presentations.
3.  **Verifier Encryption Key ($P_{V}$):** An ephemeral public key provided by the Verifier to secure the data transfer.

---

## 4. Logical Dataflow (The VC Handshake)

### Phase I: Credential Storage
1.  **Hardware Attestation:** $H$ verifies the device has a TEE/SE.
2.  **Encryption:** $I$ issues a signed VC. $H$ encrypts this VC using a hardware-protected master key ($K_{M}$) before saving to local storage.

### Phase II: Presentation Request
1.  **Discovery:** $V$ sends a **Presentation Request** to $H$ containing:
    * `Input_Descriptors`: Specific fields required (e.g., `name`, `license_number`).
    * `Verifier_DID`: The identity of the requester.
    * `Public_Key_V`: $P_{V}$ for the secure delivery channel.
    * `Nonce`: A challenge to ensure freshness.

### Phase III: Subject Authorization
1.  **Consent UI:** $H$ resolves the `Verifier_DID` against the **Trust Registry** (Entry #3 in Draft Notes) and prompts the user.
2.  **Biometric Gate:** The HSM releases the keys required to generate a Verifiable Presentation *only* upon successful biometric authentication.

### Phase IV: Verifiable Presentation (VP) Delivery
1.  **VP Generation:** $H$ extracts the requested fields and signs them with $S_{H}$ to create a Verifiable Presentation.
2.  **Peer-to-Peer Encryption:** $H$ re-encrypts the VP using the Verifier's public key ($P_{V}$).
    * $Ciphertext = Encrypt_{P_{V}}(VP + Nonce)$
3.  **Transmission:** $H$ returns the encrypted VP to $V$.

---

## 5. Security Principles

### 5.1 Hardware-Bound Presentation
Unlike software-only wallets, the private key $S_{H}$ never leaves the TEE. A "Presentation" cannot be spoofed or replayed because the hardware requires a fresh biometric trigger for every unique `Nonce`.

### 5.2 Purpose Binding & Non-Repudiation
Every VP includes a `Purpose_Statement` and an `Expiry_Timestamp`. Because the VP is signed by the Holder's hardware-backed key, it provides an immutable record of what was shared and why.

### 5.3 Verifier Accountability
The **Verifier** must provide a valid `did:sviap` that is cross-referenced with the **Operator Trust Hierarchy**. Unverified DIDs trigger "Non-Registered" warnings (Entry #3).

---
*End of Protocol Specification*
