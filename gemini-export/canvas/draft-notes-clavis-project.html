Entry #10: Архитектура хранения: Encrypted Document Store (No-DB Approach)

*Дата: 24 марта 2026 г.*

Вместо традиционной реляционной базы данных (SQL), CLAVIS использует гибридную схему «Индекс + Контейнеры». Это исключает риск компрометации всех данных сразу и упрощает работу с форматом JSON-LD (Verifiable Credentials).

**1. Мета-Индекс (Encrypted Index)**

  • **Технология:** `EncryptedSharedPreferences`.
  • **Функция:** Хранит только метаданные, необходимые для построения UI (списка документов).
  • **Состав:** ID документа, тип (Медицина/Финансы), заголовок, дата выпуска.
  • **Безопасность:** Расшифровывается при входе в приложение для отображения главного экрана. Не содержит PII (персональных данных).

    • **2. Документные Контейнеры (Encrypted Blobs)**

  • **Технология:** Индивидуальные зашифрованные файлы (или записи в Blob-хранилище).
  • **Функция:** Каждый документ (паспорт, диплом, выписка) хранится как отдельный зашифрованный JSON-объект.
  • **Безопасность:** Расшифровка происходит «лениво» (lazy loading) — только в момент санкционированного запроса от Verifier.
  • **Преимущество:** Удаление одного документа (Right to be Forgotten) происходит физически на уровне файловой системы, не оставляя следов в логах БД.

    • **3. Логика работы программы (Workflow)**

    1. **Idle State:** Все данные на диске — это зашифрованные фрагменты.

    2. **UI Build:** Приложение считывает Индекс и показывает пользователю "плитки" доступных документов.

    3. **Authorization:** При поступлении запроса от Verifier, приложение находит нужный файл по ID из Индекса, запрашивает биометрию и расшифровывает *только этот конкретный JSON*.

    4. **Memory Clean:** После передачи данных Verifier-у, расшифрованный объект немедленно стирается из оперативной памяти.

    **4. Преимущества для проекта:**

  • **Масштабируемость:** Система не тормозит при увеличении количества документов.
  • **Безопасность:** Компрометация одного ключа доступа не дает доступа ко всему архиву.
  • **Совместимость:** Прямая поддержка JSON-LD/VC форматов без необходимости маппинга в таблицы SQL.

    • Entry #11: Заметки для слайдов: Безопасность и Регуляторика

    *Дата: 24 марта 2026 г.*

    **Ключевой тезис для инвесторов и экспертов (Slide Bullet):**

    > «В системе CLAVIS отсутствует понятие "центральной базы данных пользователя". Мы заменили монолитное хранилище на децентрализованную систему изолированных зашифрованных контейнеров (Encrypted Document Store).»

    **Почему это важно (Selling Points):**

    1. **Отсутствие "Honey Pot":** Взлом приложения или кража части данных не дает доступа ко всему архиву. Нет единой таблицы, которую можно «выгрузить».

    2. **Privacy by Design:** Мы не мапим (не перекладываем) паспортные данные в таблицы базы данных. Мы храним оригинальный Verifiable Credential (JSON-LD) в «холодном» зашифрованном виде.

    3. **Compliance (GDPR/OAIC):** Реализация «права на забвение» (Right to be Forgotten) становится тривиальной технической операцией — физическим удалением файла документа без необходимости сложной очистки логов и индексов БД.

    4. **Resilience (Отказоустойчивость):** Даже если один файл данных поврежден, это никак не влияет на доступность и целостность остальных документов.

    Entry #12: Семантическая совместимость и отраслевые стандарты (Industry Schemas)

    *Дата: 26 марта 2026 г.*

    Для того чтобы CLAVIS был "plug-and-play" для бизнеса, мы отказываемся от собственных определений полей в пользу глобальных словарей. Каждый документ в CLAVIS — это JSON-LD объект с четко определенным контекстом (`@context`).

    **1. Основные используемые словари (Vocabularies):**

  • **Личные данные и контакты:** **Schema.org**.

    • * Используем типы `Person`, `PostalAddress`, `ContactPoint`. Это стандарт, который понимают Google, Microsoft и миллионы веб-сайтов.

  • **Медицинские данные:** **HL7 FHIR (Fast Healthcare Interoperability Resources)**.

    • * Каждый медицинский документ в CLAVIS — это фактически "FHIR Resource" (например, `Patient`, `Observation`, `Immunization`). Любая современная госпитальная система сможет прочитать эти данные без дополнительной настройки.

  • **Финансовые данные:** **ISO 20022** и стандарты **Consumer Data Right (CDR)** (специфично для Австралии).

    • * Позволяет банкам и финтех-приложениям получать выписки и данные о счетах в привычном для них банковском формате.

  • **Образование и дипломы:** **Open Badges** или **ELM (European Learning Model)**.

    • **2. Механизм "Контекста" в JSON-LD:**

    Внутри каждого документа CLAVIS есть ссылка на схему:

    `"@context": ["https://www.w3.org/2018/credentials/v1", "https://schema.org/"]`

    Это гарантирует, что поле `familyName` в CLAVIS — это ровно то же самое поле, что и в базе данных Verifier-а.

    **3. Преимущества для проекта (Selling Points):**

  • **Zero-Mapping Integration:** Программистам на стороне Verifier (например, в страховой компании) не нужно писать код для парсинга "формата CLAVIS". Они просто используют стандартные библиотеки для работы с FHIR или Schema.org.
  • **Глобальное доверие:** Использование стандартов HL7 и ISO делает проект "взрослым" в глазах регуляторов и корпораций.
  • **Будущая совместимость:** Если завтра появится новый стандарт (например, для углеродного следа), CLAVIS просто добавляет новую ссылку в `@context`, не меняя архитектуру приложения.

    • Entry #13: Слайд-стратегия: "Мы говорим на вашем языке" (Zero-Mapping Strategy)

    *Дата: 26 марта 2026 г.*

    Эта заметка предназначена для формирования визуального и смыслового ряда в презентации для корпоративных клиентов (B2B) и госсектора (B2G).

    **1. Визуальная метафора (Slide Visual):**

    Слева — иконка смартфона с CLAVIS. Справа — три больших "слота" (Банк, Больница, Гос-сервис). Между ними — прямая линия без промежуточных "переходников".

    **2. Заголовок слайда:**

    > «Интеграция без боли: CLAVIS говорит на языке ваших систем».

    **3. Ключевые тезисы (Bullet Points):**

  • **Никаких проприетарных форматов:** Мы не заставляем вас изучать «формат CLAVIS». Данные передаются в стандартах, которые ваши IT-системы уже знают (FHIR, ISO 20022, Schema.org).
  • **Zero-Mapping:** Вашим разработчикам не нужно перенастраивать таблицы в базах данных. Поля из кошелька пользователя (например, `familyName` или `blood_test_result`) автоматически ложатся в соответствующие поля ваших систем.
  • **Снижение TCO (Total Cost of Ownership):** Стоимость внедрения CLAVIS в 10 раз ниже, чем у любой другой ID-системы, за счет отсутствия этапа «кастомной разработки интеграционных шлюзов».
  • **Мгновенный комплаенс:** В Австралии интеграция с **CDR (Consumer Data Right)** встроена в протокол «из коробки».

    • **4. Эффектная фраза для спикера (The "Closer"):**

    > «Когда вы открываете дверь пользователю с CLAVIS, вам не нужно менять замок или перестраивать дом. Мы просто передаем вам ключ, который уже идеально подходит к вашим дверям».

    Entry #14: Выборочное раскрытие данных через Меркле-деревья (Selective Disclosure)

    *Дата: 26 марта 2026 г.*

    Эта технология позволяет пользователю предоставлять только те части документа, которые необходимы верификатору, сохраняя остальную информацию в тайне.

    **1. Техническая реализация в файловой модели:**

  • Каждый документ (JSON-LD) внутри контейнера структурирован как **Merkle Tree**.
  • **Эмитент (Issuer)** подписывает только **Merkle Root** документа.
  • Приложение CLAVIS хранит все «листья» (поля) и промежуточные хэши.

    • **2. Сценарий "Минимальной достаточности":**

  • Верификатору (например, при аренде авто) нужны только "Имя" и "Право на вождение".
  • CLAVIS извлекает из зашифрованного файла документа эти два поля и генерирует для них **Merkle Proof**.
  • Верификатор проверяет подпись Эмитента по корню дерева, не имея доступа к остальным полям (домашний адрес, медицинские ограничения и т.д.).

    • **3. Роль в базе данных (Encrypted Document Store):**

  • Это избавляет от необходимости хранить «обрезанные» копии документов для разных случаев. У вас всегда один полный файл, но вы можете «отщипнуть» от него любую комбинацию полей с сохранением юридической силы подписи.

    • **4. Заметка для слайдов (The "Privacy Filter" Slide):**

  • **Визуал:** Паспорт, закрытый черной маской, в которой прорезаны только маленькие окошки для Имени и Фото.
  • **Слоган:** «Ваш паспорт — ваши правила. Делитесь только тем, что действительно нужно».
  • **Аргумент:** Это решение полностью соответствует принципу **Data Minimization** (минимизация данных) из GDPR и австралийских законов о приватности.

    • Entry #15: Фокус для Proof of Concept (PoC)

    *Дата: 26 марта 2026 г.*

    Чтобы избежать распыления ресурсов, PoC должен доказать три фундаментальных тезиса:

    1. **Hardware-to-Data Binding:** Данные физически невозможно расшифровать без аппаратного ключа и биометрии.

    2. **Privacy Granularity:** Использование Меркле-деревьев позволяет "отщипнуть" от документа только нужные поля (Selective Disclosure).

    3. **Semantic Standard:** Данные внутри — это не просто текст, а готовый к употреблению JSON-LD (Schema.org/FHIR).

    **Заметка для слайда "PoC Success Criteria":**

  • «Мы не просто создали приложение. Мы создали hardware-gated шлюз для семантических данных».
  • «Наш PoC нативно интегрирован в Android Keystore, что делает его защищенным от копирования на уровне процессора».

    • Entry #16: Сценарий для правительства: "Zero-Error Healthcare Admission"

    *Дата: 26 марта 2026 г.*

    Медицинский сценарий является ключевым для обоснования государственного внедрения CLAVIS. Он решает проблему "административного шума" и врачебных ошибок.

    **1. Проблема (The Pain Point):**

    Ежегодно в Австралии тратятся миллиарды долларов на исправление ошибок, вызванных неверными данными при госпитализации (аллергии, несовместимые лекарства). Традиционные "бумажные" формы или разрозненные БД не гарантируют актуальности.

    **2. Решение CLAVIS:**

  • **Источник Истины:** Данные подписаны Эмитентом (Минздрав или Лаборатория).
  • **Selective Disclosure:** Пациент сам решает, какой уровень доступа дать врачу (например, "Emergency Access" открывает всё, "Routine Visit" — только общие данные).
  • **Синхронизация с FHIR:** Данные из кошелька напрямую попадают в электронную карту госпиталя без ручного ввода.

    • **3. Заметка для слайда "Impact on Healthcare":**

  • «Снижение времени регистрации пациента на 90%».
  • «Нулевой риск ошибок при вводе критических медицинских данных (аллергии, группа крови)».
  • «Полный суверенитет пациента над чувствительными диагнозами».

    • Entry #17: Визуальный якорь: Фотография в дереве Меркле

    *Дата: 26 марта 2026 г.*

    Для физической верификации (в больнице, банке или на проходной) текстовых данных недостаточно. Необходим механизм, исключающий передачу телефона другому лицу.

    **1. Механика "Face-to-Data Binding":**

  • Фотография пользователя встроена в структуру Verifiable Credential.
  • При запросе данных Верификатор получает зашифрованный пакет, содержащий: [Нужные поля] + [Фото] + [Merkle Proof].
  • Приложение Верификатора сначала проверяет криптографическую валидность (что фото не подменено), а затем выводит его на весь экран для визуального сравнения.

    • **2. Заметка для слайдов (Slide "The Human Factor"):**

  • **Визуал:** Экран смартфона верификатора, где крупно отображается фото пациента и галочка "Verified by CLAVIS".
  • **Тезис:** «Мы защищаем не только данные, но и сам процесс идентификации. Фотография — это неотъемлемая часть криптографического дерева, гарантирующая, что перед вами именно владелец документов».

    • **3. Технический нюанс (Для PoC):**

  • Чтобы не перегружать память, в Меркле-дерево может быть включен хэш фотографии высокого разрешения, но для быстрой верификации передается оптимизированная (Thumbnail) версия, также подтвержденная промежуточным хэшем.

    • Entry #18: Физические каналы передачи данных (Proximity Data Exchange)

    *Дата: 26 марта 2026 г.*

    Для сценария личного присутствия (больница, банк, государственное ведомство) CLAVIS должен поддерживать несколько уровней взаимодействия, в зависимости от оборудования верификатора.

    **1. Канал A: QR-код (Verifier-Initiated)**

  • **Механика:** Больница выводит на экран (или печатает на стойке) динамический QR-код.
  • **Процесс:** Пользователь сканирует его приложением CLAVIS. Код содержит `Request_URL` и `Session_ID`. Телефон устанавливает защищенное соединение и "заливает" данные в систему больницы.
  • **Плюсы:** Не требует специального оборудования (нужен только экран или бумага).

    • **2. Канал Б: NFC (Near Field Communication) — "Tap to Verify"**

  • **Механика:** Самый быстрый и интуитивный способ, аналогичный Apple/Google Pay.
  • **Процесс:** Пользователь подносит телефон к терминалу (считывателю). Происходит мгновенный хэндшейк (Handshake), обмен публичными ключами и передача Verifiable Presentation.
  • **Плюсы:** Самый высокий уровень безопасности (требует физической близости в несколько сантиметров).

    • **3. Канал В: Bluetooth Low Energy (BLE) / Wi-Fi Aware**

  • **Механика:** Используется для сценариев, где нужно передать много данных (например, медкарту с рентгеновскими снимками) без интернета.
  • **Процесс:** Устройства находят друг друга по Bluetooth, создают временную локальную сеть и передают пакет данных.

    • **4. Специальные устройства (The Terminal Problem):**

    Для правительственных учреждений (границы, полиция) рекомендуется использование **CLAVIS-совместимых терминалов**:

  • Это могут быть обычные планшеты со специализированным ПО.
  • Это могут быть защищенные киоски самообслуживания, где NFC-ридер встроен в корпус.

    • Entry #19: Сценарий "Proof of Presence" (Доказательство присутствия)

    *Дата: 26 марта 2026 г.*

    Физическое взаимодействие дает нам дополнительный фактор безопасности — **геолокацию и время**.

    **Заметка для слайдов (Slide "The Physical Gateway"):**

  • **Визуал:** Пользователь прикладывает телефон к планшету врача. На планшете мгновенно появляется фото пациента и его критические данные.
  • **Аргумент:** «CLAVIS — это не просто заполнение форм в браузере. Это физический ключ к услугам. Мы используем международный стандарт **ISO 18013-5**, что позволяет нашему приложению работать даже там, где нет сотовой связи (в подвалах больниц или в удаленных районах)».

    • **Ключевой посыл для Правительства:**

    «Мы превращаем обычный смартфон в **Smart Card нового поколения**. Вам не нужно выдавать гражданам новые пластиковые карты. Вам достаточно установить ПО на текущие планшеты сотрудников, и они смогут принимать данные через NFC или QR так же легко, как принимают платежи».

    Entry #20: Механика физического взаимодействия (ISO 18013-5 Compliance)

    *Дата: 26 марта 2026 г.*

    CLAVIS реализует двухэтапную модель взаимодействия при личном присутствии, полностью соответствующую международному стандарту ISO 18013-5.

    **Этап 1: Device Engagement (Установление связи)**

    Это момент, когда два устройства «узнают» о существовании друг друга.

  • **Способ А (NFC Tap):** Самый интуитивный. Устройства соприкасаются, обмениваются техническими параметрами канала.
  • **Способ Б (QR Scan):** Если NFC недоступен. Верификатор показывает QR, Холдер сканирует. QR содержит ключи для создания зашифрованного Bluetooth-канала.

    • **Этап 2: Data Retrieval (Передача данных)**

    После того как канал установлен и пользователь прошел биометрию:

  • Данные передаются в зашифрованном виде (Peer-to-Peer) напрямую с телефона на планшет.
  • **Важно:** Интернет не требуется. Это работает в автономном режиме (Offline Mode).
  • **Безопасность:** Канал защищен сессионными ключами, которые удаляются сразу после завершения проверки.

    • **Заметка для слайда "Offline Verification":**

  • **Тезис:** «CLAVIS работает везде: от подземных парковок до удаленных ферм. Мы используем стандарт ISO 18013-5, который позволяет безопасно передавать личность без интернета через NFC или Bluetooth».
  • **Аргумент:** «Это не просто 'показ картинки' на экране. Это криптографический обмен данными между процессорами двух устройств».

    • Entry #21: Юридическая ответственность Verifier: Подписанный запрос (Signed Request)

    *Дата: 26 марта 2026 г.*

    Для обеспечения полной прозрачности и защиты прав пользователя, CLAVIS вводит концепцию «Двустороннего цифрового рукопожатия».

    **1. Суть механики:**

    Верификатор не просто «спрашивает» данные, он отправляет **подписанное обязательство**. Это исключает сценарии, когда организация может заявить: «Мы не просили эти данные, пользователь сам их предоставил».

    **2. Юридическая ценность:**

  • **Non-repudiation (Неотрекаемость):** Подпись верификатора привязана к его официальному DID в государственном реестре. Это юридический документ.
  • **Audit Trail:** В локальном «сейфе» пользователя хранится история: «26 марта Клиника X запросила данные А и Б для цели Ц». Это основа для любых судебных претензий в случае утечки данных на стороне клиники.

    • **3. Интеграция с Trust Registry:**

    При получении запроса приложение CLAVIS сверяет публичный ключ подписи с реестром. Если подпись валидна, но организация помечена как «Registered» (а не «Verified»), приложение автоматически подсвечивает те поля в запросе, которые выходят за рамки стандартных полномочий этой организации (Anomaly Detection).

    **4. Заметка для слайдов (Slide "Mutual Accountability"):**

  • **Визуал:** Два свитка с печатями, соединяющиеся в один замок.
  • **Тезис:** «Ответственность — это улица с двусторонним движением. В CLAVIS каждая проверка — это юридически обязывающий контракт».
  • **Аргумент:** «Мы защищаем организацию от ложных обвинений и пользователя — от несанкционированного сбора данных. Подписанный запрос — это страховой полис для обеих сторон».

    • Entry #22: Динамическая подпись запроса vs Статичный манифест

    *Дата: 26 марта 2026 г.*

    Для предотвращения атак типа "Replay Attack" (повторное использование запроса) и обеспечения актуальности данных, CLAVIS использует модель динамического подписания.

    **1. Уровни подписи:**

  • **Организационный уровень (Static):** Долгосрочный сертификат Верификатора, подтверждающий его личность и статус в Реестре.
  • **Транзакционный уровень (Dynamic):** Каждый конкретный запрос данных подписывается сервером Верификатора "на лету".

    • **2. Состав динамического запроса (JWS - JSON Web Signature):**

  • `iat` (Issued At): Точное время создания запроса.
  • `exp` (Expires): Время, после которого запрос недействителен (например, +5 минут).
  • `nonce`: Случайное число, гарантирующее уникальность сессии.
  • `aud` (Audience): URL сайта или ID приложения, где происходит запрос.

    • **3. Как это выглядит для разработчика:**

    Веб-мастер не подписывает каждый запрос вручную. Вместо этого он интегрирует **CLAVIS SDK** на свой сервер. Когда пользователь заходит на сайт:

    1. Сервер автоматически генерирует запрос.

    2. Подписывает его ключом организации.

    3. Отправляет пользователю (через QR или Direct Link).

    **4. Заметка для слайдов (Slide "Real-time Accountability"):**

  • **Визуал:** Сравнение статичной печати на бумаге и динамического QR-кода с бегущими цифрами времени.
  • **Тезис:** «Безопасность в реальном времени. Каждый запрос в CLAVIS уникален, защищен от копирования и ограничен во времени».
  • **Аргумент:** «Это исключает возможность подделки запроса или его перехвата для использования на фишинговых сайтах. Если время истекло — ключ не сработает».

    *Дата: 26 марта 2026 г.*

    Entry #25: Кейс "Прозрачная Аренда" (Rental Market Data Sovereignty)

    *Дата: 26 марта 2026 г.*

    Рынок аренды жилья в Австралии — это критическая зона риска. Текущая модель "загрузи PDF-паспорт на портал" создает гигантские "Honey Pots" (базы-приманки), которые нарушают все принципы приватности.

    **1. Проблема: Концентрация vs Децентрализация**

  • **Текущая ситуация:** Данные миллионов арендаторов концентрируются на 2-3 крупных порталах. Это делает их целью №1 для хакеров. Агентства хранят копии документов годами, даже если арендатору отказали.
  • **Решение CLAVIS:** Данные остаются в телефоне пользователя. Агентство получает не "копию паспорта", а **криптографическое подтверждение личности** и финансовой состоятельности.

    • **2. Механика "Доказательства дохода" (Income Proof):**

  • Вместо передачи выписки из банка (где видны все траты), CLAVIS использует **Merkle Proof**.
  • Агентство запрашивает: "Подтвердите доход выше $X в неделю".
  • Кошелек проверяет подписанную банком справку и выдает ответ: **"Confirmed" (Да)**. Агентство не видит трат пользователя, оно видит только результат проверки.

    • **3. Смарт-Контракт на удаление (Retention Contract):**

  • В "Подписанном запросе" (Entry #21) агентство обязано указать срок хранения.
  • Если заявка на аренду отклонена, CLAVIS автоматически (через протокол) отправляет требование на удаление. Если агентство не предоставляет "Certificate of Deletion", его статус в Реестре (Registry) понижается.

    • **4. Заметка для слайдов (Slide "The End of the Rental Honey Pot"):**

  • **Визуал:** Сравнение. Слева: Огромный сейф портала недвижимости, который взламывают. Справа: Множество маленьких защищенных смартфонов, связанных с агентством временными "нитями" доступа.

### Entry #10: Архитектура хранения: Encrypted Document Store (No-DB Approach)
*Дата: 24 марта 2026 г.*

Вместо традиционной реляционной базы данных (SQL), CLAVIS использует гибридную схему «Индекс + Контейнеры». Это исключает риск компрометации всех данных сразу и упрощает работу с форматом JSON-LD (Verifiable Credentials).

**1. Мета-Индекс (Encrypted Index)**
* **Технология:** `EncryptedSharedPreferences`.
* **Функция:** Хранит только метаданные, необходимые для построения UI (списка документов).
* **Состав:** ID документа, тип (Медицина/Финансы), заголовок, дата выпуска. 
* **Безопасность:** Расшифровывается при входе в приложение для отображения главного экрана. Не содержит PII (персональных данных).

**2. Документные Контейнеры (Encrypted Blobs)**
* **Технология:** Индивидуальные зашифрованные файлы (или записи в Blob-хранилище).
* **Функция:** Каждый документ (паспорт, диплом, выписка) хранится как отдельный зашифрованный JSON-объект.
* **Безопасность:** Расшифровка происходит «лениво» (lazy loading) — только в момент санкционированного запроса от Verifier.
* **Преимущество:** Удаление одного документа (Right to be Forgotten) происходит физически на уровне файловой системы, не оставляя следов в логах БД.

**3. Логика работы программы (Workflow)**
1. **Idle State:** Все данные на диске — это зашифрованные фрагменты.
2. **UI Build:** Приложение считывает Индекс и показывает пользователю "плитки" доступных документов.
3. **Authorization:** При поступлении запроса от Verifier, приложение находит нужный файл по ID из Индекса, запрашивает биометрию и расшифровывает *только этот конкретный JSON*.
4. **Memory Clean:** После передачи данных Verifier-у, расшифрованный объект немедленно стирается из оперативной памяти.

**4. Преимущества для проекта:**
* **Масштабируемость:** Система не тормозит при увеличении количества документов.
* **Безопасность:** Компрометация одного ключа доступа не дает доступа ко всему архиву.
* **Совместимость:** Прямая поддержка JSON-LD/VC форматов без необходимости маппинга в таблицы SQL.

### Entry #11: Заметки для слайдов: Безопасность и Регуляторика
*Дата: 24 марта 2026 г.*

**Ключевой тезис для инвесторов и экспертов (Slide Bullet):**
> «В системе CLAVIS отсутствует понятие "центральной базы данных пользователя". Мы заменили монолитное хранилище на децентрализованную систему изолированных зашифрованных контейнеров (Encrypted Document Store).»

**Почему это важно (Selling Points):**
1. **Отсутствие "Honey Pot":** Взлом приложения или кража части данных не дает доступа ко всему архиву. Нет единой таблицы, которую можно «выгрузить».
2. **Privacy by Design:** Мы не мапим (не перекладываем) паспортные данные в таблицы базы данных. Мы храним оригинальный Verifiable Credential (JSON-LD) в «холодном» зашифрованном виде.
3. **Compliance (GDPR/OAIC):** Реализация «права на забвение» (Right to be Forgotten) становится тривиальной технической операцией — физическим удалением файла документа без необходимости сложной очистки логов и индексов БД.
4. **Resilience (Отказоустойчивость):** Даже если один файл данных поврежден, это никак не влияет на доступность и целостность остальных документов.

### Entry #12: Семантическая совместимость и отраслевые стандарты (Industry Schemas)
*Дата: 26 марта 2026 г.*

Для того чтобы CLAVIS был "plug-and-play" для бизнеса, мы отказываемся от собственных определений полей в пользу глобальных словарей. Каждый документ в CLAVIS — это JSON-LD объект с четко определенным контекстом (`@context`).

**1. Основные используемые словари (Vocabularies):**

* **Личные данные и контакты:**  **Schema.org**. 
    * Используем типы `Person`, `PostalAddress`, `ContactPoint`. Это стандарт, который понимают Google, Microsoft и миллионы веб-сайтов.
* **Медицинские данные:**  **HL7 FHIR (Fast Healthcare Interoperability Resources)**.
    * Каждый медицинский документ в CLAVIS — это фактически "FHIR Resource" (например, `Patient`, `Observation`, `Immunization`). Любая современная госпитальная система сможет прочитать эти данные без дополнительной настройки.
* **Финансовые данные:** **ISO 20022** и стандарты **Consumer Data Right (CDR)** (специфично для Австралии).
    * Позволяет банкам и финтех-приложениям получать выписки и данные о счетах в привычном для них банковском формате.
* **Образование и дипломы:** **Open Badges** или **ELM (European Learning Model)**.

**2. Механизм "Контекста" в JSON-LD:**
Внутри каждого документа CLAVIS есть ссылка на схему:
`"@context": ["https://www.w3.org/2018/credentials/v1", "https://schema.org/"]`
Это гарантирует, что поле `familyName` в CLAVIS — это ровно то же самое поле, что и в базе данных Verifier-а.

**3. Преимущества для проекта (Selling Points):**
* **Zero-Mapping Integration:** Программистам на стороне Verifier (например, в страховой компании) не нужно писать код для парсинга "формата CLAVIS". Они просто используют стандартные библиотеки для работы с FHIR или Schema.org.
* **Глобальное доверие:** Использование стандартов HL7 и ISO делает проект "взрослым" в глазах регуляторов и корпораций.
* **Будущая совместимость:** Если завтра появится новый стандарт (например, для углеродного следа), CLAVIS просто добавляет новую ссылку в `@context`, не меняя архитектуру приложения.

### Entry #14: Выборочное раскрытие данных через Меркле-деревья (Selective Disclosure)
*Дата: 26 марта 2026 г.*

Эта технология позволяет пользователю предоставлять только те части документа, которые необходимы верификатору, сохраняя остальную информацию в тайне.

**1. Техническая реализация в файловой модели:**
* Каждый документ (JSON-LD) внутри контейнера структурирован как **Merkle Tree**.
* **Эмитент (Issuer)** подписывает только **Merkle Root** документа.
* Приложение CLAVIS хранит все «листья» (поля) и промежуточные хэши.

**2. Сценарий "Минимальной достаточности":**
* Верификатору (например, при аренде авто) нужны только "Имя" и "Право на вождение".
* CLAVIS извлекает из зашифрованного файла документа эти два поля и генерирует для них **Merkle Proof**.
* Верификатор проверяет подпись Эмитента по корню дерева, не имея доступа к остальным полям (домашний адрес, медицинские ограничения и т.д.).

**3. Роль в базе данных (Encrypted Document Store):**
* Это избавляет от необходимости хранить «обрезанные» копии документов для разных случаев. У вас всегда один полный файл, но вы можете «отщипнуть» от него любую комбинацию полей с сохранением юридической силы подписи.

**4. Заметка для слайдов (The "Privacy Filter" Slide):**
* **Визуал:** Паспорт, закрытый черной маской, в которой прорезаны только маленькие окошки для Имени и Фото.
* **Слоган:** «Ваш паспорт — ваши правила. Делитесь только тем, что действительно нужно».
* **Аргумент:** Это решение полностью соответствует принципу **Data Minimization** (минимизация данных) из GDPR и австралийских законов о приватности.

### Entry #15: Фокус для Proof of Concept (PoC)
*Дата: 26 марта 2026 г.*

Чтобы избежать распыления ресурсов, PoC должен доказать три фундаментальных тезиса:
1.  **Hardware-to-Data Binding:** Данные физически невозможно расшифровать без аппаратного ключа и биометрии.
2.  **Privacy Granularity:** Использование Меркле-деревьев позволяет "отщипнуть" от документа только нужные поля (Selective Disclosure).
3.  **Semantic Standard:** Данные внутри — это не просто текст, а готовый к употреблению JSON-LD (Schema.org/FHIR).

**Заметка для слайда "PoC Success Criteria":**
* «Мы не просто создали приложение. Мы создали hardware-gated шлюз для семантических данных».
* «Наш PoC нативно интегрирован в Android Keystore, что делает его защищенным от копирования на уровне процессора».

### Entry #16: Сценарий для правительства: "Zero-Error Healthcare Admission"
*Дата: 26 марта 2026 г.*

Медицинский сценарий является ключевым для обоснования государственного внедрения CLAVIS. Он решает проблему "административного шума" и врачебных ошибок.

**1. Проблема (The Pain Point):**
Ежегодно в Австралии тратятся миллиарды долларов на исправление ошибок, вызванных неверными данными при госпитализации (аллергии, несовместимые лекарства). Традиционные "бумажные" формы или разрозненные БД не гарантируют актуальности.

**2. Решение CLAVIS:**
* **Источник Истины:** Данные подписаны Эмитентом (Минздрав или Лаборатория).
* **Selective Disclosure:** Пациент сам решает, какой уровень доступа дать врачу (например, "Emergency Access" открывает всё, "Routine Visit" — только общие данные).
* **Синхронизация с FHIR:** Данные из кошелька напрямую попадают в электронную карту госпиталя без ручного ввода.

**3. Заметка для слайда "Impact on Healthcare":**
* «Снижение времени регистрации пациента на 90%».
* «Нулевой риск ошибок при вводе критических медицинских данных (аллергии, группа крови)».
* «Полный суверенитет пациента над чувствительными диагнозами».

### Entry #17: Визуальный якорь: Фотография в дереве Меркле
*Дата: 26 марта 2026 г.*

Для физической верификации (в больнице, банке или на проходной) текстовых данных недостаточно. Необходим механизм, исключающий передачу телефона другому лицу.

**1. Механика "Face-to-Data Binding":**
* Фотография пользователя встроена в структуру Verifiable Credential.
* При запросе данных Верификатор получает зашифрованный пакет, содержащий: [Нужные поля] + [Фото] + [Merkle Proof].
* Приложение Верификатора сначала проверяет криптографическую валидность (что фото не подменено), а затем выводит его на весь экран для визуального сравнения.

**2. Заметка для слайдов (Slide "The Human Factor"):**
* **Визуал:** Экран смартфона верификатора, где крупно отображается фото пациента и галочка "Verified by CLAVIS".
* **Тезис:** «Мы защищаем не только данные, но и сам процесс идентификации. Фотография — это неотъемлемая часть криптографического дерева, гарантирующая, что перед вами именно владелец документов».

**3. Технический нюанс (Для PoC):**
* Чтобы не перегружать память, в Меркле-дерево может быть включен хэш фотографии высокого разрешения, но для быстрой верификации передается оптимизированная (Thumbnail) версия, также подтвержденная промежуточным хэшем.

### Entry #18: Физические каналы передачи данных (Proximity Data Exchange)
*Дата: 26 марта 2026 г.*

Для сценария личного присутствия (больница, банк, государственное ведомство) CLAVIS должен поддерживать несколько уровней взаимодействия, в зависимости от оборудования верификатора.

**1. Канал A: QR-код (Verifier-Initiated)**
* **Механика:** Больница выводит на экран (или печатает на стойке) динамический QR-код.
* **Процесс:** Пользователь сканирует его приложением CLAVIS. Код содержит `Request_URL` и `Session_ID`. Телефон устанавливает защищенное соединение и "заливает" данные в систему больницы.
* **Плюсы:** Не требует специального оборудования (нужен только экран или бумага).

**2. Канал Б: NFC (Near Field Communication) — "Tap to Verify"**
* **Механика:** Самый быстрый и интуитивный способ, аналогичный Apple/Google Pay.
* **Процесс:** Пользователь подносит телефон к терминалу (считывателю). Происходит мгновенный хэндшейк (Handshake), обмен публичными ключами и передача Verifiable Presentation.
* **Плюсы:** Самый высокий уровень безопасности (требует физической близости в несколько сантиметров).

**3. Канал В: Bluetooth Low Energy (BLE) / Wi-Fi Aware**
* **Механика:** Используется для сценариев, где нужно передать много данных (например, медкарту с рентгеновскими снимками) без интернета.
* **Процесс:** Устройства находят друг друга по Bluetooth, создают временную локальную сеть и передают пакет данных.

**4. Специальные устройства (The Terminal Problem):**
Для правительственных учреждений (границы, полиция) рекомендуется использование **CLAVIS-совместимых терминалов**:
* Это могут быть обычные планшеты со специализированным ПО.
* Это могут быть защищенные киоски самообслуживания, где NFC-ридер встроен в корпус.

### Entry #19: Сценарий "Proof of Presence" (Доказательство присутствия)
*Дата: 26 марта 2026 г.*

Физическое взаимодействие дает нам дополнительный фактор безопасности — **геолокацию и время**.

**Заметка для слайдов (Slide "The Physical Gateway"):**
* **Визуал:** Пользователь прикладывает телефон к планшету врача. На планшете мгновенно появляется фото пациента и его критические данные. 
* **Аргумент:** «CLAVIS — это не просто заполнение форм в браузере. Это физический ключ к услугам. Мы используем международный стандарт **ISO 18013-5**, что позволяет нашему приложению работать даже там, где нет сотовой связи (в подвалах больниц или в удаленных районах)».

### Entry #20: Механика физического взаимодействия (ISO 18013-5 Compliance)
*Дата: 26 марта 2026 г.*

CLAVIS реализует двухэтапную модель взаимодействия при личном присутствии, полностью соответствующую международному стандарту ISO 18013-5.

**Этап 1: Device Engagement (Установление связи)**
Это момент, когда два устройства «узнают» о существовании друг друга.
* **Способ А (NFC Tap):** Самый интуитивный. Устройства соприкасаются, обмениваются техническими параметрами канала.
* **Способ Б (QR Scan):** Если NFC недоступен. Верификатор показывает QR, Холдер сканирует. QR содержит ключи для создания зашифрованного Bluetooth-канала.

**Этап 2: Data Retrieval (Передача данных)**
После того как канал установлен и пользователь прошел биометрию:
* Данные передаются в зашифрованном виде (Peer-to-Peer) напрямую с телефона на планшет.
* **Важно:** Интернет не требуется. Это работает в автономном режиме (Offline Mode).
* **Безопасность:** Канал защищен сессионными ключами, которые удаляются сразу после завершения проверки.

**Заметка для слайда "Offline Verification":**
* 
* **Тезис:** «CLAVIS работает везде: от подземных парковок до удаленных ферм. Мы используем стандарт ISO 18013-5, который позволяет безопасно передавать личность без интернета через NFC или Bluetooth».
* **Аргумент:** «Это не просто 'показ картинки' на экране. Это криптографический обмен данными между процессорами двух устройств».

### Entry #21: Юридическая ответственность Verifier: Подписанный запрос (Signed Request)
*Дата: 26 марта 2026 г.*

Для обеспечения полной прозрачности и защиты прав пользователя, CLAVIS вводит концепцию «Двустороннего цифрового рукопожатия». 

**1. Суть механики:**
Верификатор не просто «спрашивает» данные, он отправляет **подписанное обязательство**. Это исключает сценарии, когда организация может заявить: «Мы не просили эти данные, пользователь сам их предоставил».

**2. Юридическая ценность:**
* **Non-repudiation (Неотрекаемость):** Подпись верификатора привязана к его официальному DID в государственном реестре. Это юридический документ.
* **Audit Trail:** В локальном «сейфе» пользователя хранится история: «26 марта Клиника X запросила данные А и Б для цели Ц». Это основа для любых судебных претензий в случае утечки данных на стороне клиники.

**3. Интеграция с Trust Registry:**
При получении запроса приложение CLAVIS сверяет публичный ключ подписи с реестром. Если подпись валидна, но организация помечена как «Registered» (а не «Verified»), приложение автоматически подсвечивает те поля в запросе, которые выходят за рамки стандартных полномочий этой организации (Anomaly Detection).

**4. Заметка для слайдов (Slide "Mutual Accountability"):**
* **Визуал:** Два свитка с печатями, соединяющиеся в один замок. 
* **Тезис:** «Ответственность — это улица с двусторонним движением. В CLAVIS каждая проверка — это юридически обязывающий контракт».
* **Аргумент:** «Мы защищаем организацию от ложных обвинений и пользователя — от несанкционированного сбора данных. Подписанный запрос — это страховой полис для обеих сторон».

### Entry #22: Динамическая подпись запроса vs Статичный манифест
*Дата: 26 марта 2026 г.*

Для предотвращения атак типа "Replay Attack" (повторное использование запроса) и обеспечения актуальности данных, CLAVIS использует модель динамического подписания.

**1. Уровни подписи:**
* **Организационный уровень (Static):** Долгосрочный сертификат Верификатора, подтверждающий его личность и статус в Реестре.
* **Транзакционный уровень (Dynamic):** Каждый конкретный запрос данных подписывается сервером Верификатора "на лету".

**2. Состав динамического запроса (JWS - JSON Web Signature):**
* `iat` (Issued At): Точное время создания запроса.
* `exp` (Expires): Время, после которого запрос недействителен (например, +5 минут).
* `nonce`: Случайное число, гарантирующее уникальность сессии.
* `aud` (Audience): URL сайта или ID приложения, где происходит запрос.

**3. Как это выглядит для разработчика:**
Веб-мастер не подписывает каждый запрос вручную. Вместо этого он интегрирует **CLAVIS SDK** на свой сервер. Когда пользователь заходит на сайт:
1. Сервер автоматически генерирует запрос.
2. Подписывает его ключом организации.
3. Отправляет пользователю (через QR или Direct Link).

**4. Заметка для слайдов (Slide "Real-time Accountability"):**
* **Визуал:** Сравнение статичной печати на бумаге и динамического QR-кода с бегущими цифрами времени. 
* **Тезис:** «Безопасность в реальном времени. Каждый запрос в CLAVIS уникален, защищен от копирования и ограничен во времени».
* **Аргумент:** «Это исключает возможность подделки запроса или его перехвата для использования на фишинговых сайтах. Если время истекло — ключ не сработает».

### Entry #23: Асимметричная модель запросов (Dynamic vs Static)
*Дата: 26 марта 2026 г.*

Для обеспечения масштабируемости системы мы вводим разные требования к технической реализации верификаторов в зависимости от их статуса.

**1. Профессиональный уровень (High-Stakes):**
* **Кто:** Финансовые, медицинские, юридические организации.
* **Технология:** Динамические JWT-запросы с коротким временем жизни.
* **Цель:** Исключить любую возможность утечки или подмены данных в критических сценариях.

**2. Базовый уровень (Low-Stakes / Convenience):**
* **Кто:** Онлайн-магазины, форумы, сервисы подписки.
* **Технология:** Статичный подписанный манифест (один раз настроил и забыл).
* **Цель:** Максимально снизить порог входа. Владельцу малого сайта достаточно один раз подписать файл ключом своей организации и выложить его на сервер.

**3. Отображение в UI (User Experience):**
* При **Динамическом** запросе приложение показывает иконку "Защищенная сессия" (синий щит).
* При **Статичном** запросе — "Базовая верификация" (серый щит). Это честно информирует пользователя об уровне ответственности запрашивающей стороны.

**4. Заметка для слайдов (Slide "Scalable Adoption"):**
* **Визуал:** Сравнение двух путей внедрения. 
* **Тезис:** «CLAVIS адаптируется под ваш бизнес. От сложной банковской интеграции до настройки за 5 минут для малого бизнеса».
* **Аргумент:** «Мы не заставляем владельца кофейни нанимать криптографа. Но мы требуем высочайших стандартов от тех, кто держит наши медицинские и финансовые секреты».

### Entry #25: Кейс "Прозрачная Аренда" (Rental Market Data Sovereignty)
*Дата: 26 марта 2026 г.*

Рынок аренды жилья в Австралии — это критическая зона риска. Текущая модель "загрузи PDF-паспорт на портал" создает гигантские "Honey Pots" (базы-приманки), которые нарушают все принципы приватности.

**1. Проблема: Концентрация vs Децентрализация**
* **Текущая ситуация:** Данные миллионов арендаторов концентрируются на 2-3 крупных порталах. Это делает их целью №1 для хакеров. Агентства хранят копии документов годами, даже если арендатору отказали.
* **Решение CLAVIS:** Данные остаются в телефоне пользователя. Агентство получает не "копию паспорта", а **криптографическое подтверждение личности** и финансовой состоятельности.

**2. Механика "Доказательства дохода" (Income Proof):**
* Вместо передачи выписки из банка (где видны все траты), CLAVIS использует **Merkle Proof**.
* Агентство запрашивает: "Подтвердите доход выше $X в неделю".
* Кошелек проверяет подписанную банком справку и выдает ответ: **"Confirmed" (Да)**. Агентство не видит трат пользователя, оно видит только результат проверки.

**3. Смарт-Контракт на удаление (Retention Contract):**
* В "Подписанном запросе" (Entry #21) агентство обязано указать срок хранения.
* Если заявка на аренду отклонена, CLAVIS автоматически (через протокол) отправляет требование на удаление. Если агентство не предоставляет "Certificate of Deletion", его статус в Реестре (Registry) понижается.

**4. Заметка для слайдов (Slide "The End of the Rental Honey Pot"):**
* **Визуал:** Сравнение. Слева: Огромный сейф портала недвижимости, который взламывают. Справа: Множество маленьких защищенных смартфонов, связанных с агентством временными "нитями" доступа. 
* **Тезис:** «Мы превращаем рынок аренды из "кошмара безопасности" в систему мгновенного доверия».
* **Аргумент для правительства:** «CLAVIS снимает с агентств недвижимости бремя ответственности за хранение терабайтов чужих паспортов. Они получают только результат верификации, а не сами риски утечки».
