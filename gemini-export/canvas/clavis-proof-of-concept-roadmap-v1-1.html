Roadmap: Proof of Concept (PoC) для CLAVIS

Цель данного PoC — продемонстрировать, что персональные данные физически защищены аппаратным модулем (TEE) и доступны только после биометрической авторизации, используя нативные средства Android.

1. Стек технологий

  • Платформа: Android (Kotlin).
  • Библиотека безопасности: Jetpack Security (Crypto).
  • Хранилище: EncryptedSharedPreferences (нативная обертка над Keystore).
  • Аутентификация: BiometricPrompt API (Class 3 / Strong).

2. Этапы реализации

Этап 1: Инициализация Master Key

При первом запуске приложение создает MasterKey с использованием аппаратного Keystore:

  • Ключ помечается как setUserAuthenticationRequired(true).
  • Добавляется флаг setInvalidatedByBiometricEnrollment(true) для защиты от несанкционированного добавления биометрии (Anti-Theft).

Этап 2: Настройка EncryptedSharedPreferences

Вместо обычных файлов используется EncryptedSharedPreferences. Это позволяет:

  • Автоматически шифровать ключи (имена полей) с помощью AES256_SIV.
  • Автоматически шифровать значения (данные) с помощью AES256_GCM.
  • Использовать аппаратный ключ из Этапа 1 для прозрачного доступа к данным.

Этап 3: Запись персональных данных (PII)

  1. Пользователь вводит тестовые данные (например, "Full Name", "Passport ID").
  2. Приложение сохраняет их через sharedPrefs.edit().putString(...).
  3. Система автоматически запрашивает биометрию для подтверждения записи (если настроено) и шифрует данные "на лету" перед сохранением в XML-файл настроек.

Этап 4: Симуляция "Запроса от Verifier"

  1. На главном экране кнопка "Предоставить данные".
  2. Вызывается системное окно BiometricPrompt.
  3. Результат: Только после успешного сканирования отпечатка/лица приложение получает доступ к EncryptedSharedPreferences, считывает данные и отображает их на экране (имитируя готовность к передаче по протоколу CLAVIS).

3. Преимущества этого подхода для PoC

  1. Нативность: Мы используем стандартные инструменты Google, что повышает доверие к безопасности решения.
  2. Надежность: Исключены ошибки ручного управления векторами инициализации (IV) и солями.
  3. Наглядность: Легко показать в логах, что без биометрии попытка прочитать SharedPrefs вызывает ошибку доступа на уровне системы.

4. Контрольные точки демонстрации

  • Показать, что данные "забываются", если в настройках телефона изменить список отпечатков пальцев.
  • Показать, что данные нельзя прочитать, просто скопировав файл настроек с телефона (они зашифрованы аппаратным ключом, привязанным к процессору).

# Roadmap: Proof of Concept (PoC) для CLAVIS

Цель данного PoC — продемонстрировать, что персональные данные физически защищены аппаратным модулем (TEE) и доступны только после биометрической авторизации, используя нативные средства Android.

## 1. Стек технологий
* **Платформа:** Android (Kotlin).
* **Библиотека безопасности:** Jetpack Security (Crypto).
* **Хранилище:** EncryptedSharedPreferences (нативная обертка над Keystore).
* **Аутентификация:** BiometricPrompt API (Class 3 / Strong).

## 2. Этапы реализации

### Этап 1: Инициализация Master Key
При первом запуске приложение создает `MasterKey` с использованием аппаратного Keystore:
* Ключ помечается как `setUserAuthenticationRequired(true)`.
* Добавляется флаг `setInvalidatedByBiometricEnrollment(true)` для защиты от несанкционированного добавления биометрии (Anti-Theft).

### Этап 2: Настройка EncryptedSharedPreferences
Вместо обычных файлов используется `EncryptedSharedPreferences`. Это позволяет:
* Автоматически шифровать ключи (имена полей) с помощью **AES256_SIV**.
* Автоматически шифровать значения (данные) с помощью **AES256_GCM**.
* Использовать аппаратный ключ из Этапа 1 для прозрачного доступа к данным.

### Этап 3: Запись персональных данных (PII)
1. Пользователь вводит тестовые данные (например, "Full Name", "Passport ID").
2. Приложение сохраняет их через `sharedPrefs.edit().putString(...)`.
3. Система автоматически запрашивает биометрию для подтверждения записи (если настроено) и шифрует данные "на лету" перед сохранением в XML-файл настроек.

### Этап 4: Симуляция "Запроса от Verifier"
1. На главном экране кнопка "Предоставить данные".
2. Вызывается системное окно `BiometricPrompt`.
3. **Результат:** Только после успешного сканирования отпечатка/лица приложение получает доступ к `EncryptedSharedPreferences`, считывает данные и отображает их на экране (имитируя готовность к передаче по протоколу CLAVIS).

## 3. Преимущества этого подхода для PoC
1. **Нативность:** Мы используем стандартные инструменты Google, что повышает доверие к безопасности решения.
2. **Надежность:** Исключены ошибки ручного управления векторами инициализации (IV) и солями.
3. **Наглядность:** Легко показать в логах, что без биометрии попытка прочитать `SharedPrefs` вызывает ошибку доступа на уровне системы.

## 4. Контрольные точки демонстрации
* Показать, что данные "забываются", если в настройках телефона изменить список отпечатков пальцев.
* Показать, что данные нельзя прочитать, просто скопировав файл настроек с телефона (они зашифрованы аппаратным ключом, привязанным к процессору).
